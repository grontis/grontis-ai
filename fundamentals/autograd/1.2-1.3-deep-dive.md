# 1.2 Autograd — the engine that makes learning possible

## The core idea in one sentence

Autograd lets PyTorch **automatically compute derivatives** of any computation you write, by secretly recording every operation into a graph and then replaying it backward.

Why does this matter? Training a model = "nudge the parameters in the direction that reduces error." To know *which direction*, you need the derivative of the error with respect to each parameter (the **gradient**). Doing that calculus by hand for a million-parameter model is impossible. Autograd does it for free.

## What `requires_grad` actually turns on

The guide's starter example (`intro.py`):

```python
import torch

x = torch.tensor(3.0, requires_grad=True)
y = x ** 2          # y = x²
y.backward()        # compute dy/dx
print(x.grad)       # 6.0, because dy/dx = 2x = 2*3
```

When you set `requires_grad=True`, you're telling PyTorch: *"track everything that happens to this tensor."* From that point on, every operation involving `x` gets recorded.

Inspect the machinery directly — this is the part the guide doesn't show you:

```python
import torch

x = torch.tensor(3.0, requires_grad=True)
y = x ** 2

print(y)                 # tensor(9., grad_fn=<PowBackward0>)
print(y.grad_fn)         # <PowBackward0 object ...>
print(y.requires_grad)   # True — it inherited tracking from x
print(x.grad)            # None — gradients don't exist until .backward()

y.backward()
print(x.grad)            # tensor(6.)
```

That `grad_fn=<PowBackward0>` is the key. `y` doesn't just store the number `9.0` — it stores *how it was made* (a power operation) and *what it was made from* (`x`). That's the "graph." `PowBackward0` is literally the recipe for the derivative of a power.

## The graph: a worked multi-step example

Real models chain many operations. Watch the graph build up:

```python
import torch

x = torch.tensor(2.0, requires_grad=True)

a = x * 3        # a = 3x
b = a + 1        # b = 3x + 1
c = b ** 2       # c = (3x + 1)²

c.backward()
print(x.grad)    # 42.0
```

Verify by hand. `c = (3x+1)²`. By the chain rule:

```
dc/dx = 2·(3x+1) · 3 = 6·(3x+1)
at x=2:  6·(3·2+1) = 6·7 = 42  ✓
```

The graph looks like `x → (×3) → a → (+1) → b → (²) → c`. `.backward()` starts at `c` and walks *backward* through each recorded operation, multiplying the local derivatives together (that's the chain rule), until it reaches `x` and deposits the result in `x.grad`.

**This is the whole trick.** No matter how deep the network, it's just this chain rule applied automatically over a longer graph.

## Gradients accumulate — the #1 gotcha

This is the single most important behavior to internalize, because it directly explains why `zero_grad()` exists in section 1.3:

```python
import torch

x = torch.tensor(3.0, requires_grad=True)

y = x ** 2
y.backward()
print(x.grad)    # 6.0

# Run the SAME computation again WITHOUT clearing:
y = x ** 2
y.backward()
print(x.grad)    # 12.0  ← not 6.0! It ADDED to the old gradient.
```

`.backward()` **adds** to `.grad`, it doesn't overwrite. PyTorch does this on purpose (it's useful for some advanced techniques), but it means *you* are responsible for clearing gradients between updates. Forget to, and your gradients pile up garbage. Clearing it:

```python
x.grad = None        # or x.grad.zero_()
```

## `torch.no_grad()` — turning the recorder off

When you *update* a parameter, that update is bookkeeping, not part of the model's math — you don't want it recorded into the graph. `torch.no_grad()` is a context manager that says "don't track anything in here":

```python
import torch

w = torch.tensor(5.0, requires_grad=True)

with torch.no_grad():
    w -= 0.1 * 2.0      # a manual update; not tracked
    # w is still a leaf with requires_grad=True, just edited in place

print(w)   # tensor(4.8000, requires_grad=True)
```

Without `no_grad()`, this in-place edit on a tracked tensor would either error or corrupt the graph. You'll use it constantly: every weight update and every evaluation pass runs under `no_grad()` (it also saves memory and time, since nothing needs to be recorded).

## The exercise, fully worked: linear regression by hand

The guide tells you to do this *without* peeking. Try it yourself first — the struggle is the point. Use this only to check against **afterward**:

```python
import torch

# 1. Make noisy data around the true line y = 2x + 1
torch.manual_seed(42)
x = torch.linspace(-3, 3, 100)
y_true = 2 * x + 1 + 0.5 * torch.randn(100)   # noise added

# 2. Parameters we want to LEARN. Start them wrong on purpose.
w = torch.tensor(0.0, requires_grad=True)
b = torch.tensor(0.0, requires_grad=True)

lr = 0.05

# 3. The learning loop
for step in range(200):
    # forward: our current guess of the line
    y_pred = w * x + b

    # loss: mean squared error — how wrong are we, on average?
    loss = ((y_pred - y_true) ** 2).mean()

    # backward: fill w.grad and b.grad
    loss.backward()

    # update: step downhill, against the gradient
    with torch.no_grad():
        w -= lr * w.grad
        b -= lr * b.grad

        # clear grads so next iteration starts clean (see the accumulate gotcha!)
        w.grad = None
        b.grad = None

    if step % 40 == 0:
        print(f"step {step:3d} | loss {loss.item():.4f} | w {w.item():.3f} | b {b.item():.3f}")

print(f"\nLearned: y = {w.item():.2f}x + {b.item():.2f}   (target: y = 2x + 1)")
```

Expected output — watch `w` crawl toward 2 and `b` toward 1:

```
step   0 | loss 14.13xx | w 0.3xx | b 0.0xx
step  40 | loss  0.5xxx | w 1.8xx | b 0.7xx
...
Learned: y = 1.98x + 0.99   (target: y = 2x + 1)
```

**Why each line matters:**

| Line | Role | What breaks if you remove it |
|---|---|---|
| `requires_grad=True` on `w,b` | marks them as things to optimize | `w.grad` is `None`, can't update |
| `loss.backward()` | computes `dloss/dw`, `dloss/db` | grads never get filled |
| `with torch.no_grad()` | update isn't recorded | error or corrupted graph |
| `w -= lr * w.grad` | step downhill | nothing learns |
| `w.grad = None` | clear for next step | grads accumulate → training diverges |

**Break it deliberately** (the guide's whole philosophy):
- Delete the two `grad = None` lines → watch the loss explode or thrash. That's the accumulation gotcha biting you live.
- Set `lr = 1.0` → loss goes to `nan`. The steps overshoot and bounce out to infinity. This is the "LR too high" row in the appendix debugging table.
- Set `lr = 0.0001` → it barely moves in 200 steps. Too timid.

When this clicks, you genuinely understand training. Everything after is the same loop with more parameters.

# 1.3 The training-loop skeleton

## Why memorize this

Every model you ever train — the Fashion-MNIST classifier in Phase 2, the GPT in Phase 4 — has **exactly this shape**. Your hand-written linear regression above *is* this skeleton; section 1.3 just swaps your manual pieces for PyTorch's batteries-included versions:

| You did by hand (1.2) | The "real" version (1.3) |
|---|---|
| `y_pred = w * x + b` | `preds = model(batch_x)` |
| `((y_pred - y_true)**2).mean()` | `loss = loss_fn(preds, batch_y)` |
| `w.grad = None; b.grad = None` | `optimizer.zero_grad()` |
| `loss.backward()` | `loss.backward()` (identical!) |
| `w -= lr*w.grad; b -= lr*b.grad` | `optimizer.step()` |

Same five moves. The `model` holds all parameters for you, the `optimizer` knows how to update them, the `loss_fn` is a prebuilt error measure.

## The skeleton, annotated

```python
for epoch in range(num_epochs):          # one epoch = one full pass over the data
    for batch_x, batch_y in dataloader:  # data comes in batches, not all at once
        batch_x, batch_y = batch_x.to(device), batch_y.to(device)  # move to GPU

        preds = model(batch_x)           # 1. FORWARD: model's predictions
        loss = loss_fn(preds, batch_y)   # 2. MEASURE: how wrong?

        optimizer.zero_grad()            # 3. CLEAR old gradients
        loss.backward()                  # 4. COMPUTE new gradients (autograd!)
        optimizer.step()                 # 5. UPDATE the weights
```

**The order of 3-4-5 is sacred.** Clear, then compute, then step. The most common ordering bug — putting `zero_grad()` *after* `backward()` — wipes the gradients you just computed, so the model never learns at all.

## A complete, runnable example

The guide's skeleton is abstract (`model`, `loss_fn`, `dataloader` undefined). Here's the smallest *complete* version using real PyTorch components — it's your linear-regression exercise rebuilt the "1.3 way." Run it and compare to your hand-written version:

```python
import torch
import torch.nn as nn

torch.manual_seed(42)
device = "cuda" if torch.cuda.is_available() else "cpu"

# --- data (same noisy line, reshaped to (N, 1) for nn.Linear) ---
x = torch.linspace(-3, 3, 100).unsqueeze(1)        # shape (100, 1)
y = 2 * x + 1 + 0.5 * torch.randn(100, 1)

# --- the three "batteries-included" pieces ---
model = nn.Linear(1, 1).to(device)                 # holds a weight + bias for us
loss_fn = nn.MSELoss()                             # mean squared error, prebuilt
optimizer = torch.optim.SGD(model.parameters(), lr=0.05)  # knows how to update

x, y = x.to(device), y.to(device)

# --- the skeleton ---
for epoch in range(200):
    preds = model(x)                # 1. forward
    loss = loss_fn(preds, y)        # 2. measure

    optimizer.zero_grad()           # 3. clear
    loss.backward()                 # 4. compute grads
    optimizer.step()                # 5. update

    if epoch % 40 == 0:
        print(f"epoch {epoch:3d} | loss {loss.item():.4f}")

# pull the learned numbers out of the model
w, b = model.weight.item(), model.bias.item()
print(f"\nLearned: y = {w:.2f}x + {b:.2f}   (target: y = 2x + 1)")
```

It learns the *same* `w≈2, b≈1`. You just delegated the bookkeeping. `model.parameters()` is the bridge: the optimizer is told *which* tensors to update, so `optimizer.zero_grad()` clears all their grads and `optimizer.step()` updates all of them — no matter if there are 2 parameters or 2 million.

## Batches and epochs (the two `for` loops)

In the toy example above I passed all 100 points at once. Real datasets are too big for that, so you split them into **batches** and use a `DataLoader`. Here's the two-loop structure with one:

```python
import torch
import torch.nn as nn
from torch.utils.data import TensorDataset, DataLoader

torch.manual_seed(42)
x = torch.linspace(-3, 3, 100).unsqueeze(1)
y = 2 * x + 1 + 0.5 * torch.randn(100, 1)

dataset = TensorDataset(x, y)
dataloader = DataLoader(dataset, batch_size=16, shuffle=True)

model = nn.Linear(1, 1)
loss_fn = nn.MSELoss()
optimizer = torch.optim.SGD(model.parameters(), lr=0.05)

for epoch in range(50):                       # outer: passes over the whole dataset
    for batch_x, batch_y in dataloader:       # inner: one batch at a time
        preds = model(batch_x)
        loss = loss_fn(preds, batch_y)
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
    if epoch % 10 == 0:
        print(f"epoch {epoch:2d} | last batch loss {loss.item():.4f}")
```

- **Epoch** = one full sweep through all your data. 50 epochs = the model saw every point 50 times.
- **Batch** = a small subset (here 16 points). With 100 points and `batch_size=16`, each epoch runs the inner loop ~7 times → ~7 weight updates per epoch.
- **`shuffle=True`** reshuffles each epoch so the model doesn't learn the *order* of the data.

Smaller batches = more frequent, noisier updates. Bigger batches = fewer, smoother updates but more memory. In Phase 4, batch size is exactly the knob you'll turn when you hit the 8 GB VRAM wall.

## `model.train()` vs `model.eval()` and the no-grad eval loop

The skeleton above is the *training* half. There's a mirror-image *evaluation* loop you'll write in Phase 2 (`evaluate(...)`). Two differences:

```python
# --- training ---
model.train()                       # turn ON dropout / batchnorm-updating
for batch_x, batch_y in train_loader:
    preds = model(batch_x)
    loss = loss_fn(preds, batch_y)
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()

# --- evaluation ---
model.eval()                        # turn OFF dropout etc. — deterministic
with torch.no_grad():               # don't track grads: faster, less memory
    for batch_x, batch_y in val_loader:
        preds = model(batch_x)
        # measure accuracy/loss, but NO backward, NO step — we're just looking
```

- `model.eval()` / `model.train()` flip the behavior of layers like Dropout and BatchNorm (you'll meet these in Phase 3). Forgetting `eval()` is the "eval accuracy weirdly low" row in the debugging table.
- `torch.no_grad()` — same one from 1.2. During evaluation you're not learning, so recording the graph is pure waste.

## Mapping it forward

Hold onto this because it pays off everywhere later:

- **Phase 2** uses this exact loop, just with `model = nn.Sequential(...)`, `loss_fn = nn.CrossEntropyLoss()`, `optimizer = Adam(...)`, and a `DataLoader` over Fashion-MNIST.
- **Phase 4's** GPT training is *the same five lines*. The transformer is more elaborate inside `model(...)`, but `zero_grad → backward → step` is untouched.

That's why the guide says "every later phase is just these ideas wearing a costume."
