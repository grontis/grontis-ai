# 1.4 The `nn.Module` pattern

## The core idea in one sentence

`nn.Module` is a **container that automatically tracks your model's parameters** (the learnable tensors), so you can define layers once and get `.parameters()`, `.to(device)`, `.train()/.eval()`, saving, and loading *for free*.

In 1.2 you managed `w` and `b` by hand: you created them with `requires_grad=True`, you remembered to pass both to your update step, you cleared both grads. That's fine for 2 parameters. The GPT in Phase 4 has *millions*, spread across dozens of layers. You cannot track those by hand. `nn.Module` is how PyTorch tracks them for you.

## The two-method contract

Every model you build follows the same shape:

```python
import torch
import torch.nn as nn

class MyModel(nn.Module):
    def __init__(self):
        super().__init__()          # ← never forget this line
        # define your layers HERE, as attributes
        self.layer1 = nn.Linear(10, 20)
        self.layer2 = nn.Linear(20, 1)

    def forward(self, x):
        # define HOW data flows through them HERE
        x = self.layer1(x)
        x = torch.relu(x)
        x = self.layer2(x)
        return x
```

Two methods, two jobs:

- **`__init__`** — *what the model is made of.* You create the layers and store them as `self.something`.
- **`forward`** — *what the model does.* You describe the path a tensor takes from input to output.

That's the whole pattern. Everything else `nn.Module` gives you is built on top of these two.

## The one line beginners forget: `super().__init__()`

```python
class Broken(nn.Module):
    def __init__(self):
        # forgot super().__init__()
        self.layer = nn.Linear(10, 1)

Broken()
# AttributeError: cannot assign module before Module.__init__() call
```

`nn.Module.__init__` sets up the internal bookkeeping dictionaries (the registries for parameters and sub-modules). If you skip `super().__init__()`, those dictionaries don't exist yet, and the moment you write `self.layer = nn.Linear(...)` PyTorch has nowhere to register it. **Always call `super().__init__()` first.**

## The magic: how assignment registers parameters

This is the part the guide doesn't show you, and it's the reason the whole pattern works. When you write `self.layer1 = nn.Linear(10, 20)` inside a module, `nn.Module` *intercepts that assignment* and records `layer1` in an internal registry. Watch it happen:

```python
import torch.nn as nn

class MyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.layer1 = nn.Linear(10, 20)
        self.layer2 = nn.Linear(20, 1)

    def forward(self, x):
        return self.layer2(torch.relu(self.layer1(x)))

model = MyModel()

# Every learnable tensor, discovered automatically:
for name, p in model.named_parameters():
    print(name, tuple(p.shape))
```

Output:

```
layer1.weight (20, 10)
layer1.bias   (20,)
layer2.weight (1, 20)
layer2.bias   (1,)
```

You never wrote "register these four tensors." You assigned two `nn.Linear` layers as attributes, and `nn.Module` walked into each one, found *its* parameters, and gave them dotted names (`layer1.weight`). This recursion is the key feature: **modules contain modules contain parameters**, and `.parameters()` flattens the whole tree.

That dotted naming is also exactly what makes saving/loading work later — hold that thought.

## Calling the model: why `model(x)`, never `model.forward(x)`

```python
model = MyModel()
x = torch.randn(4, 10)        # a batch of 4 inputs, each size 10

preds = model(x)              # ✅ correct
# preds = model.forward(x)    # ❌ works, but never do this
```

`nn.Module` defines `__call__`, so `model(x)` invokes `forward(x)` *plus* important hooks around it (the machinery that makes `train()`/`eval()` and other features work). Calling `forward` directly skips those hooks. **Rule: always call `model(x)`.** You'll see this everywhere — `preds = model(batch_x)` in the training skeleton is exactly this.

## Connecting back to 1.3: this is what `model.parameters()` was

Remember the 1.3 example? `optimizer = torch.optim.SGD(model.parameters(), lr=0.05)`. Now you can see what `model.parameters()` actually returns — the flattened list of every registered tensor:

```python
model = MyModel()
optimizer = torch.optim.SGD(model.parameters(), lr=0.01)

# the optimizer now holds references to all 4 tensors above.
# optimizer.zero_grad()  clears ALL their .grad
# optimizer.step()       updates ALL of them
# ...no matter how many layers you add.
```

This is the payoff. In 1.2 you manually wrote `w.grad = None; b.grad = None` and `w -= lr*w.grad; b -= lr*b.grad` — two tensors, four lines. With `nn.Module` + an optimizer, those same operations cover *every* parameter in the tree, and your training loop never changes as the model grows.

## A complete, runnable example: linear regression, the `nn.Module` way

The [1.3 deep dive](./1.2-1.3-deep-dive.md) used a bare `nn.Linear(1, 1)`. Here's the *same problem* wrapped in your own `nn.Module` subclass, so you see the full pattern end to end. It learns the identical `w≈2, b≈1`:

```python
import torch
import torch.nn as nn

torch.manual_seed(42)
device = "cuda" if torch.cuda.is_available() else "cpu"

# --- data: the same noisy line y = 2x + 1 ---
x = torch.linspace(-3, 3, 100).unsqueeze(1)        # (100, 1)
y = 2 * x + 1 + 0.5 * torch.randn(100, 1)

# --- the model as a proper nn.Module subclass ---
class LinearRegression(nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = nn.Linear(1, 1)              # one weight, one bias

    def forward(self, x):
        return self.linear(x)

model = LinearRegression().to(device)              # .to() moves ALL params at once
loss_fn = nn.MSELoss()
optimizer = torch.optim.SGD(model.parameters(), lr=0.05)

x, y = x.to(device), y.to(device)

# --- the exact same 1.3 skeleton ---
for epoch in range(200):
    preds = model(x)                # 1. forward  (calls forward() via __call__)
    loss = loss_fn(preds, y)        # 2. measure
    optimizer.zero_grad()           # 3. clear  (every param)
    loss.backward()                 # 4. compute grads
    optimizer.step()                # 5. update (every param)

    if epoch % 40 == 0:
        print(f"epoch {epoch:3d} | loss {loss.item():.4f}")

w, b = model.linear.weight.item(), model.linear.bias.item()
print(f"\nLearned: y = {w:.2f}x + {b:.2f}   (target: y = 2x + 1)")
```

Compare this to the 1.3 version. The training loop is *byte-for-byte identical*. The only thing that changed is that the model is now a class you wrote — which means you can put **anything** inside `forward`, and the loop still works. That's the door to every architecture in this guide.

## Building blocks you'll actually use

You rarely wire layers one-by-one. Two helpers cover most cases:

### `nn.Sequential` — a straight pipe

When data just flows through layers in order with no branching, `nn.Sequential` saves you a `forward`:

```python
import torch.nn as nn

# These two models are equivalent.

# (a) explicit subclass
class MLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(784, 128),
            nn.ReLU(),
            nn.Linear(128, 10),
        )
    def forward(self, x):
        return self.net(x)

# (b) sometimes you'll even use Sequential directly as the model
model = nn.Sequential(
    nn.Linear(784, 128),
    nn.ReLU(),
    nn.Linear(128, 10),
)
```

This is the exact MLP shape you'll build in **Phase 2** for Fashion-MNIST (784 inputs = a flattened 28×28 image, 10 outputs = 10 clothing classes). You're closer to Phase 2 than it looks.

### `nn.ModuleList` — a list that registers

The trap: if you store layers in a plain Python list, **they don't register** and `.parameters()` won't find them.

```python
class Broken(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = [nn.Linear(10, 10) for _ in range(3)]   # ❌ plain list

class Works(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList(nn.Linear(10, 10) for _ in range(3))  # ✅

print(len(list(Broken().parameters())))   # 0  — invisible to the optimizer!
print(len(list(Works().parameters())))    # 6  — 3 layers × (weight + bias)
```

A plain list is just a Python object as far as `nn.Module`'s assignment-interception is concerned — it doesn't look *inside* it. `nn.ModuleList` is a registering container. **This matters directly in Phase 4:** the GPT stacks N transformer blocks, and you'll hold them in exactly this — `self.blocks = nn.ModuleList(...)` (or `nn.Sequential(*blocks)`). Use a plain list there and your transformer silently won't train.

## `.to(device)`, `.train()`, `.eval()` — module-wide switches

Because the module tracks every parameter and sub-module, these one-liners apply to the *whole tree*:

```python
model.to("cuda")     # moves every parameter to the GPU in one call
model.train()        # puts every sub-module into training mode
model.eval()         # puts every sub-module into eval mode
```

You met `model.train()` / `model.eval()` in the 1.3 deep dive — now you know *why* one call flips the whole model: it recurses through the registry and sets the mode on every layer. Layers like `nn.Dropout` and `nn.BatchNorm` (Phase 3) read that mode to change their behavior. This recursion is the same reason `model.to(device)` is enough — you never move parameters individually.

## Saving and loading: `state_dict`

Section 2.4 will tell you to checkpoint with `torch.save(model.state_dict(), ...)`. Here's what that object *is* so it's not a mystery later:

```python
model = LinearRegression()
print(model.state_dict())
# OrderedDict([('linear.weight', tensor([[...]])),
#              ('linear.bias',   tensor([...]))])
```

A `state_dict` is just an ordered dictionary mapping **those dotted parameter names** (`linear.weight`) to their current tensor values. Remember the naming from the "magic" section above? This is where it pays off — the names are the keys. Round-trip it:

```python
torch.save(model.state_dict(), "checkpoints/best.pt")

fresh = LinearRegression()                       # new model, random weights
fresh.load_state_dict(torch.load("checkpoints/best.pt"))
fresh.eval()                                     # set eval mode after loading
```

`load_state_dict` matches keys by name and copies the values in. That's why you load into *the same architecture* — the names and shapes have to line up. Saving the `state_dict` (just the numbers) rather than the whole object is the recommended, portable way to checkpoint.

## Break it deliberately (the guide's whole philosophy)

Run these and predict the outcome *before* you do:

- **Delete `super().__init__()`** from a module → `AttributeError: cannot assign module before Module.__init__() call`. Now you'll recognize it instantly when it happens for real.
- **Store layers in a plain list** instead of `nn.ModuleList` → `model.parameters()` comes back shorter (or empty), the optimizer never updates those layers, and that part of the model is frozen at its random init. Loss stalls for no obvious reason.
- **Call `model.forward(x)` instead of `model(x)`** in a model that has Dropout → in eval mode it'll still drop activations, because you skipped the hooks. Subtle and nasty; this is why the rule is absolute.
- **Add a `self.scale = 2.0`** (a plain float) in `__init__` and use it in `forward` → fine, it works, but notice it does *not* appear in `.parameters()`. Only `nn.Parameter` / layers register. (If you wanted it learnable, you'd wrap it: `self.scale = nn.Parameter(torch.tensor(2.0))`.)

## Mapping it forward

This is the single most reused pattern in the whole guide:

- **Phase 2** — your Fashion-MNIST MLP and CNN are `nn.Module` subclasses. The `nn.Sequential` MLP above is literally a first draft of it.
- **Phase 3** — the ResNet "residual block" is an `nn.Module` whose `forward` does `return self.layers(x) + x`. The skip connection lives *inside* `forward` — something you could only do because you control that method.
- **Phase 4** — the GPT is `nn.Module`s all the way down: a `Head`, a `MultiHeadAttention`, a `FeedForward`, a `Block`, all assembled into the top-level model. `self.blocks = nn.ModuleList(...)`, `model.parameters()` into the optimizer, `torch.save(model.state_dict())` to checkpoint — every piece you just learned, reused verbatim.

When the guide says "every later phase is just these ideas wearing a costume," `nn.Module` is the costume rack.
